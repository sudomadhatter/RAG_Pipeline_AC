## 1. Change Summary

### What Changed and Why

The Socratic teaching pipeline was originally designed around **pure RAG retrieval** — the Librarian searched the databases and the LLM inferred what to teach from semantic results. This is probabilistic and non-deterministic, meaning two students on the same lesson could receive different curricula.

**The RKP Pivot:** Required Knowledge Points (RKPs) replace pure RAG as the curriculum backbone. Each lesson now has a deterministic `{lesson_id}_rkp.json` manifest authored by the CFI team. RKPs define WHAT to teach; the 6-Search RAG provides HOW to teach it and WITH WHAT authority.

### Architectural Changes at a Glance

| Before (V2.0) | After (V2.1) |
|---------------|-------------|
| Pure RAG discovery → LLM infers lesson content | RKP manifest → deterministic curriculum skeleton |
| 3-lane Librarian (all DB2) | 6-Search architecture (2 DB1 + 4 DB2) |
| "Teach Me" single button | 4-step lesson flow: Overview → Flashcards → Socratic → Quiz |
| Agent 1 receives student data + RAG | Agent 1 receives RKP + RAG only (no student data) |
| Agent 2 receives lesson plan only | Agent 2 receives lesson plan + struggle data + Pre-Bunk + Global Traps |
| RAG runs on "Teach Me" click → latency | RAG triggers on flashcard start → zero latency (Flashcard Buffer) |
| Cache by lesson_id with implicit TTL | Cache tied to mastery lifecycle, fresh on every retake |
| No flashcards | Anki-style swipe deck in Drawer, sourced from RKP manifest |
| No audio | Optional 5-10 min podcast per lesson |

## 2. PRD Changes

### 2.1 New Functional Requirements

#### FR36: Required Knowledge Points (RKP) Manifest ← D4, D10

Each of the 34 active PPL lessons has one RKP manifest file (`{lesson_id}_rkp.json`) authored by the CFI team. Each manifest contains 3–6 knowledge points representing what a DPE expects a student to articulate during an oral exam.

**FR36-A:** RKP manifests are the **single source of truth** for lesson content. All downstream systems (flashcards, Librarian searches, lesson planning, quiz generation, audio) are driven by the RKP manifest.

**FR36-B: Graceful Failure.** If a malformed RKP JSON is loaded (missing fields, wrong enums, parse error):
- Student sees: *"This lesson is currently undergoing a scheduled curriculum update from our Chief Flight Instructors. Please try another module."*
- Backend fires: P1 webhook alert with malformed file path and parse error.
- System does NOT fall back to RAG-only mode. A silent fallback creates "ghost mode" where SAR telemetry is poisoned.

**FR36-C: Schema.** Each RKP contains: `id`, `title`, `why` (DPE perspective), `knowledge` (oral-exam-level content), `acs_elements[]`, `far_references[]`, `bridge_keys[]`. Full schema in Section 4 of the ACS Coverage Gap Analysis.

**FR36-D: Coverage Rules.** 3-6 RKPs per lesson (target 4). Every ACS element mapped to the lesson must be covered by at least one RKP. One RKP can span multiple elements if closely related.

#### FR37: Flashcard Deck ← D7, D8, D13

**FR37-A:** Each lesson has an Anki-style flashcard deck rendered in the Drawer panel. Cards are derived directly from the RKP manifest JSON — no backend processing required.

**FR37-B: Card Content.**
- **Front:** RKP `title` + `why` field (from the DPE's perspective)
- **Back:** RKP `knowledge` + `far_references`

**FR37-C: Swipe Mechanics.**
- Swipe Right = "I know this" → card removed from deck
- Swipe Left = "Don't know" → card returns to stack
- Completion = all cards swiped right → deck marked complete

**FR37-D: Gating.** Not enforced. Students can skip to Socratic (their responsibility). V3 may use swipe-left data to inform Agent 1 targeting.

**FR37-E: Flashcard Buffer.** The flashcard step is an **architectural buffer**. The 6-Search RAG triggers the millisecond the student starts the deck. The 2-5 minutes of active study gives the backend uncontested compute time to run all searches, build the lesson plan, and cache it. By "Begin Socratic," the plan is already cached.

#### FR38: Audio Lesson (Optional Podcast) ← D1, D2

**FR38-A:** Each lesson may have an optional 5-10 minute podcast episode. Two virtual flight instructors have a natural conversation covering every RKP in the lesson.

**FR38-B:** Audio is supplementary — not required, not gated. If `audio_file` is `null` in the RKP manifest, the player is hidden.

**FR38-C:** Production uses Google NotebookLM "Deep Dive" → light polish → MP3 conversion → Firebase Storage upload. V3 upgrade path: scripted re-recording with Google Cloud TTS.

**FR38-D:** Storage: `gs://aviationchat.appspot.com/lesson_audio/{lesson_id}_audio.mp3`

#### FR39: 4-Step Lesson Flow ← D7, D9, D11

**FR39-A: The Flow.** The "Teach Me" button (FR5) is replaced by a 4-step pedagogical progression:

| Step | Name | Surface | Description |
|------|------|---------|-------------|
| ① | Lesson Overview | Chat | Agent generates brief overview + explains flashcard system |
| ② | Flashcard Deck | Drawer | Anki-style swipe deck from RKP manifest |
| ③ | Socratic Understanding | Chat | Agent 2 runs 4-pillar Q&A using cached lesson plan |
| ④ | Mastery Quiz | Drawer | MCQ + SJT, 80% pass gate |

**FR39-B: State-Based Unlocking.**
- `mastery_status == "not_started"`: Strict linear (1→2→3→4). Buttons unlock sequentially.
- `mastery_status >= "seen"`: All 4 buttons visible, unlocked from start. Respects adult learners' time.

**FR39-C: Retake.** Every retake generates a FRESH lesson plan using updated struggle data. No stale cache.

#### FR23-A: Pre-Cache Strategy → Mastery Lifecycle Cache ← D14

**UPDATED.** Cache lifecycle is now event-driven by mastery transitions:

```
ON LOGIN → Pre-cache top study queue lesson (if not already cached)
ON FLASHCARD START → Verify cache or trigger 6-Search RAG
ON "BEGIN SOCRATIC" → Serve cached plan to Agent 2
ON LESSON COMPLETED → Cache CLEARED
ON DIFFERENT LESSON → Save current cache, load/build new
ON RETAKE → Generate FRESH plan with updated struggle data
```

No TTL timers. Cache persists until mastery state transition.

### 2.3 Agent Data Injection Split (Section 5 Update) ← D15

> Agent 1 builds the map. Agent 2 drives the car.

**Agent 1 — The Lesson Planner (Batch Job)**
- Receives: RKP Manifest + 6-Search RAG results
- Does NOT receive: student struggle data, Pre-Bunk, Global Traps
- Job: Build curriculum-grounded `LessonPlan` with 4 `SocraticNode`s

**Agent 2 — The Socratic Teacher (Real-Time)**
- Receives: cached `LessonPlan` + Tier 2 ACS Ledger + Tier 1 Global Profile + Pre-Bunk (FR34) + Global Traps (FR35)
- Job: Facilitate Socratic conversation, adapt in real time based on student's struggle history

**Why:** Agent 1 is a batch job (runs during flashcards) — target answers don't change per student. Agent 2 is real-time — needs struggle data to personalize pacing and emphasis.

### 2.4 Librarian / Swarm RAG Update (Section 6 Update) ← D3, D12, D16, D17

**UPDATED.** The Librarian's search topology evolves from 3-lane symmetric (all DB2) to **6-Search dual-database** with Bridge Key hops.

## 3. Architecture Changes

### 3.1 The 6-Search RAG Architecture ← D3, D12, D16, D17

> **Core Principle:** DB1 teaches (scenarios, explanations, common errors). DB2 cites (authoritative FAA regulatory/guidance text). Bridge Keys provide deterministic linking — no semantic guessing.

#### Routing Table

| # | Search Name | Database | Query Source | What It Finds | Chunks Returned |
|---|-------------|----------|-------------|---------------|----------------|
| 1 | **RKP Lesson** | DB1 | K/R/S-tagged RKPs from manifest | Teaching content: Oral Standard, Expert Deep Dive, Common Errors | **5** |
| 2 | **RM Module** | DB1 | Entire parent ACS Task (module) | ADM/Human Factors: scenarios, examples across ALL lessons in module | **5** |
| 3 | **Legal** | DB2 (hybrid) | `reg_keys` from K-tagged RKPs | FAR regulatory text (14 CFR Part 61, 91, etc.) | **fetch 5, keep top 3** |
| 4 | **Safety** | DB2 (hybrid) | `doc_keys` from R-tagged RKPs | PHAK/AIM/AC safety guidance | **fetch 5, keep top 3** |
| 5 | **Application** | DB2 (hybrid) | `doc_keys` from S-tagged RKPs | AIM procedures, AC practical guidance | **fetch 5, keep top 3** |
| 6 | **RM Bridge Hop** | DB2 (hybrid) | Bridge Keys extracted from Search #2 | ADM-specific ACs, PHAK Ch.17 | **fetch 5, keep top 3** |

**Total max chunks to Agent 1:** 22 (5+5 from DB1, 3+3+3+3 from DB2 after hybrid re-ranking)

#### Execution Flow

```
1. LOAD RKP manifest → extract K/R/S elements

2. PARALLEL (5 searches):
   ├─ DB1 #1: RKP Lesson (return 5 chunks)
   ├─ DB1 #2: RM Module (return 5 chunks)
   ├─ DB2 #3: Legal (fetch 5, keep top 3 via hybrid re-rank)
   ├─ DB2 #4: Safety (fetch 5, keep top 3 via hybrid re-rank)
   └─ DB2 #5: Application (fetch 5, keep top 3 via hybrid re-rank)

3. SEQUENTIAL (after #2 completes):
   └─ DB2 #6: RM Bridge Hop (fetch 5, keep top 3 via hybrid re-rank)
        Extract Bridge Keys from #2 results
        Query DB2 for ADM-related ACs

4. AGGREGATE all 6 results (max 22 chunks) → Agent 1 + RKP manifest
```

#### Search Governance — Result Limits & Temperature ← Daniel's Directive

| Parameter | Value | Rationale |
|-----------|-------|-----------|
| **DB1 chunks returned** | 5 per search | DB1 has the teaching content — we want richer context from curriculum and module. |
| **DB2 fetch / keep** | Fetch 5, keep top 3 | DB2 is hybrid RAG (BM25 + neural). Over-fetch lets the re-ranker surface the best chunks. Prevents context stuffing. |
| **Total max chunks to Agent 1** | 22 | DB1: 5+5 = 10. DB2: 3+3+3+3 = 12. Keeps context window manageable (~5,000-7,000 tokens of RAG). |
| **Agent 1 temperature** | **0.3** | Low creativity — lesson plans must be structurally correct and curriculum-aligned. Not 0.0 (too rigid for scenario diversity). |
| **Agent 2 temperature** | **0.6** | Current value (Socratic Teacher). Enough variation for natural conversation. |
| **Vertex AI Search** | N/A | Search retrieval is a ranking engine, not generative — temperature doesn't apply. |

> [!NOTE]
> **Why Vertex Search has no temperature:** Vertex AI Discovery Engine (`discoveryengine`) uses BM25 + neural ranking to retrieve documents. It's NOT running a generative model. There is no temperature to tune. Query expansion and spell correction are the relevant tuning knobs, and they're already set to `AUTO`.

> [!WARNING]
> **🔧 TUNING REQUIRED POST-IMPLEMENTATION:** The chunk counts, search queries, and agent prompts defined here are initial values. During Story 4.XX.2 (6-Search Librarian Refactor) development and QA, the team MUST:
> 1. **Test each search lane** with real RKP manifests across multiple lessons
> 2. **Evaluate result quality** — are the chunks relevant? Is the re-ranker surfacing the right content?
> 3. **Dial in the query construction prompts** — the `legal_query`, `safety_query`, `rm_query` etc. templates need iterative refinement based on actual search results
> 4. **Tune chunk counts** up or down per lane based on context window usage and output quality
> 5. **Confirm Agent 1 temperature** produces structurally diverse yet accurate lesson plans
>
> This is standard RAG tuning work. Plan for 1-2 iteration cycles after initial implementation.

#### Bridge Key Retention ← D16

Bridge Keys remain in DB1 lesson plans (`### 4. Bridge Keys` section) alongside RKP `far_references` and `bridge_keys` fields. Both coexist:

1. RKP `far_references`: Used by DB2 Legal lane (Search #3)
2. RKP `bridge_keys`: Used by DB2 Safety/Application lanes (Search #4, #5)
3. DB1 lesson plan Bridge Keys: Power the RM Bridge Hop (Search #6) and Expert Witness Q&A pipeline

Zero maintenance cost, additive coverage.

### 3.2 New Component: `rkp_loader.py` ← D4, D10

**Location:** `backend/data/rkp_loader.py`  
**Schema:** `backend/schemas/rkp.py`

```python
# Pydantic schema for RKP validation
class RequiredKnowledgePoint(BaseModel):
    id: str                          # "RKP_01"
    title: str                       # Flashcard front headline (5-8 words)
    why: str                         # DPE perspective (1-2 sentences)
    knowledge: str                   # Oral-exam-level content (2-4 sentences)
    acs_elements: List[str]          # ["PA.I.B.K3"]
    far_references: List[str]        # ["14 CFR 39", "14 CFR 91.403"]
    bridge_keys: List[str]           # ["PHAK Ch 9", "AC 39-7D"]

class RKPManifest(BaseModel):
    lesson_id: str                   # "PPL_PA_I_B_03"
    title: str                       # "Airworthiness Directives (ADs)"
    acs_task_reference: str          # "Area I, Task B"
    acs_element_keys: List[str]      # All ACS element codes
    required_knowledge_points: List[RequiredKnowledgePoint]
    audio_file: Optional[str]        # "{lesson_id}_audio.mp3" or null
```

**Graceful failure:** `rkp_loader.load(lesson_id)` raises `RKPValidationError` on malformed JSON. Caught at the API layer → "Lesson Unavailable" response + P1 webhook.

### 3.3 New Pattern: Flashcard Buffer ← D13

**What:** The flashcard step provides 2-5 minutes of "free" compute time for the backend to run the full 6-Search RAG and build the lesson plan.

**Trigger sequence:**
1. Student clicks "Start Flashcards" → frontend event fires
2. API receives `/api/lessons/{lesson_id}/start-flashcards`
3. Backend kicks off async `build_lesson_plan()` task
4. Student swipes flashcards for 2-5 minutes
5. By "Begin Socratic" click → plan already cached in Firestore

**Architectural benefit:** Eliminates the latency vs. depth tradeoff. No spinner, no streaming compromises, no token budget trading.

### 3.4 Cache Architecture Update ← D14

**Collection:** `users/{uid}/socratic_cache/{lesson_id}`

```json
{
  "lesson_plan": { ... },           // Full LessonPlan JSON
  "rkp_manifest_hash": "sha256...", // For future staleness detection
  "created_at": "2026-04-03T...",
  "status": "ready|building|error"
}
```

**Lifecycle:**
- Created: on flashcard start (or login pre-cache)
- Served: on "Begin Socratic" click
- Cleared: on lesson completion (quiz passed → mastery transition)
- Replaced: on retake (fresh build with updated struggle data)
- Saved: on lesson switch (preserved under original lesson_id)

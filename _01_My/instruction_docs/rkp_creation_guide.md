# Creating New RKP Manifests — What I Need From You

## TL;DR

An **RKP** (Required Knowledge Point) is a JSON manifest that packages a lesson module into the format our ingestion pipeline, flashcard UI, and RAG system all consume. Think of it as the **DNA blueprint** for a lesson — it tells every downstream system what to teach, what to cite, and what to quiz on.

You currently have **34 RKPs** for Area I (Tasks A–H), plus the newer lessons in Areas III, VI, VII, IX,
and XI. Use this guide whenever you author **additional** RKP manifests.

> [!IMPORTANT]
> **Quiz quality bar:** when you write the 8 quiz questions per lesson, follow **`quiz_authoring_guide.md`**
> (same folder). It reconstructs the gold standard from the Area I bank — the SJT design ("all options
> legal, pick the safest"), the four perspectives, the difficulty levers, and the explanation standard
> (real FARs + real accident data, never invented). The Area I bank is the reference; the new-lesson
> questions are being rewritten and are **not** a model.

### 1. Which ACS Tasks/Elements does each module cover?

This is the most important decision. Tell me:

> You can give me the ACS code list, or just describe the topic and I'll map it to the ACS codes for you. Example: *"A module on normal takeoffs and landings"* → I'll find the matching PA codes.

### 2. The Lesson Title

A short, human-readable title for the module card. Keep it 3-6 words.

**Examples from existing modules:**
| Lesson ID | Title |
|---|---|
| `PPL_PA_I_A_01` | Privileges & Limitations |
| `PPL_PA_I_B_04` | Flying with Inoperative Equipment (91.213) |
| `PPL_PA_I_G_02` | The Powerplant & Propeller |

### 3. The Raw Teaching Content

For each **knowledge point** within the module, I need:

| Field | What It Is | Example |
|---|---|---|
| **Title** | 2-5 word name for this specific knowledge point | "Certification & Currency" |
| **Why** | One sentence: why does this matter for a student pilot? | "Ensures pilots meet baseline legal and safety standards before carrying passengers." |
| **Knowledge** | The core teaching paragraph — plain text, factually complete. This is the "textbook answer." | *(see existing RKPs for length/tone)* |
| **FAR References** | Which 14 CFR sections are relevant | `["14 CFR 61.56", "14 CFR 91.205"]` |
| **Bridge Keys** | Which FAA documents back this up — **document-level tokens only** (no chapter/section in the key; that's what matches DB2). Chapter detail goes in the prose. | `["FAA-H-8083-25C", "AC 61-98D"]` |

> [!IMPORTANT]
> **Bridge keys are a hard contract, not a nicety.** Every lesson must ship with non-empty,
> **document-level** `doc_keys` (e.g. `FAA-H-8083-25C`, `AC 61-98D`, `AIM`, `14 CFR 91`) that resolve to
> real hits in the FAA library (DB2). Empty or chapter-level keys silently break answer verification.
> See **`bridge_key_guide.md`** (same folder) for the full contract, the root cause, and how to prove it.
>
> **(2026-06-16)** This is now **enforced at ingest**, not just advised: `src/utils/schema.py` already
> rejects empty `doc_keys` (`min_length=1` + strip-`N/A`), and the contract is being upgraded so a
> `doc_key` outside DB2's `document_tags` vocabulary **fails the gate** (not just warns). Author at
> document granularity from the start — a key like `FAA-H-8083-25C (PHAK Ch 6)` or `AIM 8-1-5` will be
> rejected. Chapter/section detail belongs in the prose, never in the machine key.

> [!IMPORTANT]
> The `knowledge` field is the **source of truth**. It must be factually complete and accurate. I will NEVER modify it. The `knowledge_formatted` field (the pretty flashcard markdown) is auto-generated by our `curriculum_components/scripts/generate_knowledge_formatted.py` script using Gemini Pro.

> [!IMPORTANT]
> **The `knowledge` field is also what the quiz author reads — the reverse contract.** Every fact a
> quiz question will test must live in a `knowledge` field, **NOT only in the `lesson_overview`.** If
> a testable concept (a cognitive mechanism, a second-order consequence) exists only in the overview,
> the student who studied the RKP flashcards can't answer it. *Real example:* the "wrong-CTAF
> interferes with pilots at other airports" consequence in `PPL_PA_III_A_01` lived only in the
> overview, so its quiz question wasn't cleanly answerable from RKP_01 — the fix is to teach it in
> `knowledge`. This is the reverse side of the **two-way contract** in `quiz_authoring_guide.md` §0:
> quizzes are authored *from* the RKPs, so make every testable fact (and its common misconception)
> explicit in `knowledge`. And keep citations **in scope** — e.g. VFR lost-comm is governed by
> 91.126 / 91.127 + light signals (AIM 4-3-13), **not** the IFR reg 91.185.

### 4. The Lesson Overview (The "Podcast Script")

A narrative essay (500-1000 words) that ties all the RKPs in the module together into a cohesive teaching story. This is what gets rendered as the lesson "overview" in the app and drives the audio/video generation.

**Tone:** Conversational expert. Like a seasoned CFI explaining it at the whiteboard — not a textbook, not a regulation.

See `lesson_overview` in `curriculum_components/rkp_manifests/PPL_PA_I_A_01_rkp.json` for the gold standard.

## The Exact RKP JSON Schema

Every RKP file follows this structure (from `curriculum_components/rkp_manifests/PPL_PA_I_A_01_rkp.json`):

```json
{
  "lesson_id": "PPL_PA_II_A_01",          // PPL_ prefix + ACS area/task + sequence
  "title": "Normal Takeoff & Climb",       // Human-readable module title
  "acs_task_reference": "Area II, Task A", // Which ACS task
  "acs_element_keys": [                    // ALL element codes this module covers
    "PA.II.A.K1",
    "PA.II.A.K2",
    "PA.II.A.R1"
  ],
  "required_knowledge_points": [           // 3-5 knowledge points per module
    {
      "id": "RKP_01",                      // Sequential within this module
      "title": "...",                      // Short name for this point
      "why": "...",                        // One-sentence importance
      "knowledge": "...",                  // Full teaching paragraph (NEVER auto-modified)
      "acs_elements": ["PA.II.A.K1"],      // Which element(s) this point addresses
      "far_references": ["14 CFR ..."],    // Regulatory citations
      "bridge_keys": ["FAA-H-8083-25C", "AC 61-98D"], // Document-level tokens — see bridge_key_guide.md
      "knowledge_formatted": ""            // LEFT BLANK — auto-generated by script
    }
  ],
  "lesson_overview": "## Title\n\n...",    // The narrative essay
  "audio_file": "PPL_PA_II_A_audio.m4a",  // Auto-hydrated by script
  "video_file": "PPL_PA_II_A_video.mp4"   // Auto-hydrated by script
}
```

## Naming Convention

| Component | Pattern | Example |
|---|---|---|
| **Lesson ID** | `PPL_PA_{AREA}_{TASK}_{SEQ}` | `PPL_PA_II_A_01` |
| **RKP File** | `{lesson_id}_rkp.json` | `PPL_PA_II_A_01_rkp.json` |
| **Curriculum Key ID** | `PA_{AREA}_{TASK}_{SEQ}` (no PPL prefix) | `PA_II_A_01` |

| **Video** | `PPL_PA_{AREA}_{TASK}_video.mp4` | `PPL_PA_II_A_video.mp4` |

# Flashcard Creation Guide

> **Read `rkp_creation_guide.md` first.** Flashcards are not a separate thing you author — they are
> the lesson's RKP manifest, rendered as cards. This guide is about the *one* flashcard-specific
> step (generating `knowledge_formatted`) and how to write RKP fields so the card teaches well.

## 0. The one idea that makes this guide short

**There is no flashcard file.** A "flashcard deck" for a lesson **is** that lesson's RKP manifest
(`curriculum_components/rkp_manifests/PPL_PA_*_rkp.json`). Each `required_knowledge_point` (RKP)
becomes exactly one flashcard. You don't write cards; you write good RKPs and run one script.

So everything in `rkp_creation_guide.md` already applies. This doc adds only: **(a)** what the
student actually sees on a card, **(b)** how each RKP field maps onto the card, and **(c)** the
single automation step that turns `knowledge` into the pretty card back.

---

## 1. What the student sees (card anatomy)

Each card flips. Front = the recall prompt; back = the answer.

```
┌──────────────────────────────┐      ┌──────────────────────────────┐
│  🧐 EXAMINER'S FOCUS         │      │  📋 REQUIRED KNOWLEDGE        │
│                              │ flip │                              │
│        {RKP.title}           │ ───▶ │  {RKP.knowledge_formatted}   │
│       "{RKP.why}"            │      │   (markdown: bold + bullets) │
│                              │      │                              │
│  Recall the rules before     │      │  [14 CFR 91.103] [AC 61-98D] │  ← FAR pills
│  flipping ↺                  │      │                              │     (RKP.far_references)
└──────────────────────────────┘      └──────────────────────────────┘
        FRONT (the prompt)                    BACK (the answer)
```

- **Front** ("🧐 Examiner's Focus"): the RKP `title` (heading) and `why` (italic, in quotes). The
  front's job is to make the student *try to recall* before they flip. It deliberately shows no
  facts.
- **Back** ("📋 Required Knowledge"): the `knowledge_formatted` markdown, with the
  `far_references` shown as badge pills along the bottom.

---

## 2. Field → card map (what renders, what doesn't)

| RKP field | Where it lands on the card | Notes |
|---|---|---|
| `title` | Front heading | Short, examiner-framed concept name |
| `why` | Front subtitle (the recall hook) | **One sentence. Do NOT put the answer here** — it kills the recall value |
| `knowledge` | **Source of truth.** Back *fallback* only | Never auto-modified; also what the quiz author reads (the reverse contract) |
| `knowledge_formatted` | Back body (rendered markdown) | Auto-generated by the script — leave it `""` in the manifest |
| `far_references` | Back badge pills | A wrong reg renders as a wrong pill, visible to the student — keep citations in scope |
| `acs_elements`, `bridge_keys` | **Do not render on the card** | They drive grading / RAG, not the flashcard |

> The back renders `knowledge_formatted || knowledge` — i.e. if `knowledge_formatted` is empty, the
> card falls back to the raw `knowledge` text. **So a card with no formatted version still works —
> it's just not pretty.** An un-run formatter is an ugly card, not a broken one. No panic.

---

## 3. Writing a card that teaches

The card is only as good as the three RKP fields behind it.

- **`title`** — a short noun phrase naming the concept being recalled ("Required Preflight
  Information", not "Regulations"). It's the cue the student associates the facts with.
- **`why`** — one sentence on *the stakes*: what breaks if the pilot doesn't know this. Frame it as
  a hook the student can fail to answer, not a restatement of the back. **Anti-example:** if the
  back is "VFR fuel minimums are 30 min day / 45 min night," the `why` must NOT say "you need 30/45
  minutes of reserve" — that gives the answer away. Say instead: "Run a tank dry and the certificate
  won't matter — what does the reg actually require?"
- **`knowledge`** — factually complete and accurate (it is the source of truth and the quiz author's
  input). Write it so it *formats* well: lead with the rule, then the specifics. A wall of unbroken
  prose produces a wall-of-text card.

---

## 4. The one automation step — generate `knowledge_formatted`

`knowledge_formatted` is the only flashcard-specific artifact, and you do **not** hand-write it.
The script reads `title` + `why` + `knowledge` and produces scannable card-ready markdown with
Gemini Pro. It **never modifies `knowledge`** — only writes `knowledge_formatted`.

```bash
# Dry run a single file first (prints, does not save):
python curriculum_components/scripts/generate_knowledge_formatted.py

# Save a single file:
python curriculum_components/scripts/generate_knowledge_formatted.py --write

# Regenerate the whole set:
python curriculum_components/scripts/generate_knowledge_formatted.py --all --write
```

**After running, eyeball the output.** It's LLM-formatted, so confirm each back is *scannable on a
small card*: a short bold lead, then a tight bullet list of the hard facts. The renderer is GitHub-
Flavored Markdown (`react-markdown` + `remark-gfm`) — **bold, bullets, headings, and tables render;
raw HTML does not.** Aim for roughly ≤120 words on the back; the card is small.

---

## 5. Upkeep — the cascade when you change a fact

The fields feed more than the card, so a single edit ripples:

1. **You edit an RKP `knowledge` field** ⇒ **re-run the formatter** (§4) so the card back matches,
   **and re-check that RKP's quiz questions** — the quiz author reads `knowledge`, so the same fact
   change may move a correct answer or a distractor (`quiz_authoring_guide.md` §0, the two-way
   contract).
2. **You change `far_references`** ⇒ the back's pills change automatically on next ingest. Keep the
   citation in scope and correct — a precise-but-wrong reg is worse than a missing one. If you don't
   know the right reg, **ask Daniel; don't let the model guess.**
3. **You add a brand-new RKP** ⇒ it becomes a new card automatically; just make sure you ran the
   formatter so it isn't a raw-text fallback card.

## 6. The ownership boundary (who handles the UI)

**You produce content; the app renders it.** The flashcard UI — the flip animation, the deck
navigation, the styling, and the dashboard "Cards" tab — is built and owned by the **app/frontend
team** (`frontend/src/components/lesson/FlashcardDeck.tsx`, `FlashcardCard.tsx`,
`frontend/src/styles/flashcard.css`, served by `GET /api/lessons/flashcard-decks`). The "unlocked"
state on a deck (it lights up once the student passes the lesson quiz / reaches `rote_level` mastery)
is also app-side logic.

**None of that is yours to touch.** Your job ends at: good RKP fields + a run of the formatter. If a
card looks wrong because of *layout* (spacing, flip, colors), that's an app bug — flag it, don't try
to fix it in the content. If a card looks wrong because of *what it says* (bad fact, ugly formatting,
answer leaked into the `why`), that's content — that's you.

---

## 7. Anti-patterns

| ❌ Don't | ✅ Do instead |
|---|---|
| Hand-edit `knowledge_formatted` | Edit `knowledge`, then re-run the formatter (it overwrites your edit anyway) |
| Put the answer in `why` | Make `why` a hook the student can fail to recall |
| Write `knowledge` as one long paragraph | Lead with the rule, then specifics — so it formats into a scannable card |
| Look for a "flashcard JSON" to author | There isn't one — the RKP manifest *is* the deck |
| Use raw HTML / unsupported markdown | Stick to GFM: bold, bullets, headings, tables |
| Invent a `far_reference` to fill the pill | Get the correct reg from Daniel; leave it out rather than guess |

---

## 8. Self-check before ingest

- [ ] Every RKP has a non-empty `why` that is a **hook, not the answer**.
- [ ] `knowledge` is factually complete (and every fact a quiz tests lives here, not only in the overview).
- [ ] You ran `generate_knowledge_formatted.py` — `knowledge_formatted` is populated (or you knowingly accept the raw fallback).
- [ ] Each back reads scannably on a small card (short bold lead + tight bullets, ~≤120 words).
- [ ] `far_references` are correct and in scope (they render as visible pills).

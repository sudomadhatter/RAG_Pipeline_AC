## 1. System Overview

The Ingestion Pipeline is a standalone, local Python CLI application responsible for transforming local raw documents (Markdown lesson plans and PDF manuals) into searchable, indexed records within Google Cloud's Vertex AI Search (Discovery Engine).

It implements a **Dual-Store Topology** as defined in the AviationChat architecture:
- **DB1 (Curriculum):** `aviation-curriculum-v1` (Unstructured, Hybrid Search)
- **DB2 (Library):** `aviation-library-v1` (Unstructured, Hybrid Search + Metadata Filtering)

---

## 2. Directory Structure & Document Lifecycle

The pipeline manages local state using a three-stage directory lifecycle for both the curriculum and library sources. This ensures a clear audit trail and prevents accidental uploads of partially edited files.

### 2.1 Curriculum (DB1) Structure

```text
c:\AGY-Projects\ingestion-Pipeline-AC\
  ├── pipeline/
  │   ├── curriculum/
  │   │   ├── new/                 <-- Author drops new/edited .md & .json pairs here
  │   │   ├── active/              <-- Pipeline moves successfully ingested files here
  │   │   ├── superseded/          <-- Pipeline moves older versions here (timestamped)
  │   │   └── manifest.json        <-- Local state summary generated by pipeline
  │   │
  │   └── library/
  │       ├── new/                 <-- Admin drops new/updated PDFs here
  │       ├── active/              <-- Ingested PDFs organized by subfolder
  │       │   ├── regulations/
  │       │   ├── handbooks/
  │       │   └── advisory_circulars/
  │       ├── superseded/          <-- Replaced PDFs (e.g., 2024 FAR replaced by 2025)
  │       └── manifest.json
```

## 3. Data Flow Architecture

The ingestion process is identical for both DB1 and DB2 pipelines, consisting of five distinct phases executed locally.

### Phase 0: AI Metadata Generation (Pre-Pipeline)
- The human Librarian drops raw `.md` (Curriculum) or `.pdf` (Library) files into the workspace.
- For Curriculum `.md` files, the Librarian prompts the AI Assistant to read the file and generate a matching `.json` sidecar containing the required metadata (ACS code, title, keywords, `reg_keys`, and `doc_keys`).
- The pipeline itself expects these `.json` files to exist before Phase 1 begins.

### Phase 1: File Discovery & Validation
- Scan the `/new/` directory for incoming files.
- Validate DB1 files: Ensure `.json` metadata matches the schema and has a corresponding `.md` content file.
- Validate DB2 files: Parse filenames to deduce category (regulation, handbook, AC).

### Phase 2: Bridge Key Verification (DB1 Only)
- Extract `reg_keys` and `doc_keys` from new DB1 lesson metadata.
- Cross-reference these keys against the currently known contents of the `library/active/` directory.
- Warn the user if a lesson references a library document that does not yet exist.

### Phase 3: GCS Upload
- Initialize Google Cloud Storage client.
- Upload files from `new/` to the respective buckets (`aviationchat-curriculum-cms` or `aviationchat-library`).
- Uses idempotent logic (overwrite if exists during full rebuilds, otherwise only upload differences).

### Phase 4: Vertex AI Search JSONL Manifest Generation
- Read all files currently in the `active/` directory plus files successfully uploaded from `new/`.
- Generate the required `xyz.jsonl` manifest required by Vertex AI Search.
  - Generates `content.uri` pointing to the `gs://` location.
  - Maps custom metadata into the `structData` field.
- Upload the `.jsonl` manifest to the root of the GCS bucket.

### Phase 5: Vertex AI Data Store Import & Lifecycle Transition
- Trigger the `importDocuments` method via the `discoveryengine_v1` Python client.
- Point the import job to the GCS URI of the newly uploaded `.jsonl` manifest.
- Await job completion.
- Upon success, move files from `new/` to `active/`, and any displaced files from `active/` to `superseded/`.

## 4. Component Design

The CLI application will be built using a modular Python structure:

```text
src/
  ├── main.py              # CLI entry point (argparse implementation)
  ├── config.py            # GCP project IDs, bucket names, data store names
  ├── pipeline/
  │   ├── base.py          # Abstract base pipeline class
  │   ├── curriculum.py    # DB1 specific logic (JSON+MD validation)
  │   └── library.py       # DB2 specific logic (PDF parsing/categorization)
  ├── gcp/
  │   ├── storage.py       # GCS bucket interaction wrappers
  │   └── vertex.py        # Discovery Engine import wrappers
  └── utils/
      ├── lifecycle.py     # new -> active -> superseded file moving logic
      └── schema.py        # Pydantic models for JSON validation
```

### Key Libraries
- `google-cloud-storage`: For Phase 3 uploads.
- `google-cloud-discoveryengine`: For Phase 5 Vertex AI triggers.
- `pydantic`: For robust runtime validation of the lesson and library metadata JSON schemas (protects against malformed data breaking the Search index).

## 6. Edge Cases & Error Handling

1. **Vertex AI Import Failures:** If Phase 5 fails (e.g., quota limits or malformed JSONL), the pipeline aborts the lifecycle transition. Files remain in `new/` to ensure manual review and retry.
2. **Orphaned Content:** A `.json` without a `.md` in the `curriculum/new/` directory throws a hard validation error before any GCP calls are made.
3. **Duplicate IDs:** If an incoming file has an ID that matches an existing file in `active/`, it's treated as an update. The old file is cleanly moved to `superseded/` to prevent clobbering the history.

# RKP Manifest Creation Skill

> **Owner:** Woz (Agent) — receives master modules from Daniel (CFI).
> **Trigger:** Daniel provides a master module `.md` file and requests RKP creation.
> **Output:** One or more `{lesson_id}_rkp.json` files in `curriculum_components/rkp_manifests/`.

---

## 1. What You Receive (Inputs)

Daniel delivers a **master module** markdown file. These live in:
`curriculum_components/curriculum_modules/`

Each master module covers **one ACS Task** (e.g., "Area I, Task A") and contains
multiple ACS elements. Each element has 4 sections:

```
## PA.I.A.K1: [Element Title]
> Context: ...

#### 1. The Oral Standard (The Direct Answer)
[2-4 sentence answer a student must articulate]

#### 2. The Expert Deep Dive (The "Textbook")
[Multi-paragraph teaching content with subsections]

#### 3. Common Errors & Gotchas
[Bullet list of traps and misconceptions]

#### 4. Bridge Keys (Metadata)
* Regs: [FAR citations]
* Docs: [PHAK chapters, ACs, handbooks]
* Keywords: [search terms]
```

---

## 2. What You Produce (Outputs)

For each master module, you create **multiple lesson-level RKP manifests**.
One master module → typically 2-5 RKP JSON files, depending on how many
ACS elements group into logical lessons.

### 2.1 The Lesson Split

Use the **ACS Element to Lesson ID Mapping** from `curriculum_components/quiz_schema.md`
(lines 118-155) as the definitive guide for which elements belong to which lesson.

If a new Area/Task has no existing mapping, propose one to Daniel for approval
before building the JSON files.

### 2.2 The Exact JSON Schema

Every RKP file MUST follow this structure exactly:

```json
{
  "lesson_id": "PPL_PA_{AREA}_{TASK}_{SEQ}",
  "title": "Human-Readable Module Title (3-6 words)",
  "acs_task_reference": "Area {N}, Task {L}",
  "acs_element_keys": ["PA.{AREA}.{TASK}.K1", "PA.{AREA}.{TASK}.K2"],
  "required_knowledge_points": [
    {
      "id": "RKP_01",
      "title": "Short headline (2-5 words)",
      "why": "One sentence: why this matters for a student pilot.",
      "knowledge": "The core teaching paragraph — plain text, factually complete. This is the textbook answer. 2-4 sentences. NEVER auto-modified after Daniel approves.",
      "acs_elements": ["PA.{AREA}.{TASK}.K1"],
      "far_references": ["14 CFR 61.56"],
      "bridge_keys": ["FAA-H-8083-25C", "AC 61-98D"],
      "knowledge_formatted": ""
    }
  ],
  "lesson_overview": "## Title\n\n[500-1000 word narrative essay]",
  "audio_file": "PPL_PA_{AREA}_{TASK}_audio.m4a",
  "video_file": "PPL_PA_{AREA}_{TASK}_video.mp4"
}
```

## 3. Field-by-Field Rules

### `lesson_id`
- Pattern: `PPL_PA_{AREA}_{TASK}_{SEQ}`
- Area uses Roman numerals: `I`, `II`, `III`, `IV`, `V`, `VI`, `VII`, `VIII`, `IX`, `X`, `XI`
- Task is a single uppercase letter: `A`, `B`, `C`, `D`
- Sequence is zero-padded 2-digit: `01`, `02`, `03`
- Example: `PPL_PA_I_A_01`, `PPL_PA_IX_B_01`

### `title`
- 3-6 words. Human-readable. Matches what students see in the app.
- Do NOT include the ACS code in the title.

### `acs_task_reference`
- Format: `"Area {N}, Task {L}"` using Roman numerals for the area number.
- Example: `"Area I, Task A"`, `"Area IX, Task B"`

### `acs_element_keys`
- ALL element codes this lesson covers. Must match the master module exactly.
- Format: `PA.{AREA}.{TASK}.{TYPE}{NUM}` where TYPE is K/R/S.

### `required_knowledge_points` (3-6 per lesson, target 4)

| Field | Source | Rules |
|---|---|---|
| `id` | Sequential | `RKP_01`, `RKP_02`, etc. Reset per lesson. |
| `title` | Derived from element heading | 2-5 words. This is the flashcard front headline. |
| `why` | Agent writes | One sentence. Why this matters. NOT "the DPE will ask." State the practical importance. |
| `knowledge` | **From master module §1 "The Oral Standard"** | 2-4 sentences. Factually complete. Include FAR numbers. **NEVER modify after Daniel approves.** |
| `acs_elements` | From master module | Which element code(s) this RKP covers. One RKP can span multiple related elements. |
| `far_references` | From master module §4 "Regs" | Specific 14 CFR citations. Use exact format: `"14 CFR 61.56"`. |
| `bridge_keys` | From master module §4 "Docs" | **DOCUMENT-LEVEL ONLY.** `"FAA-H-8083-25C"`, NOT `"FAA-H-8083-25C (PHAK Ch 6)"`. Chapter detail goes in the prose, not in the key. See bridge_key_guide.md §3.3. |
| `knowledge_formatted` | **LEFT BLANK** — auto-generated by script | Set to `""`. Run `generate_knowledge_formatted.py` after JSON is written. |

### `lesson_overview`
- 500-1000 word narrative essay tying all RKPs together.
- Tone: Conversational expert CFI at the whiteboard.
- Must cover every RKP in the lesson.
- Include the "checkride trap" — a scenario a DPE would stack.
- See `PPL_PA_I_A_01_rkp.json` `lesson_overview` as the gold standard.

### `audio_file` / `video_file`
- Auto-hydrated by `generate_knowledge_formatted.py` script.
- Pattern: `PPL_PA_{AREA}_{TASK}_audio.m4a` / `PPL_PA_{AREA}_{TASK}_video.mp4`
- These are per-TASK, not per-lesson (all lessons under the same task share one audio/video).

## 4. Coverage Rules (Non-Negotiable)

1. **Every ACS element** in the master module must be covered by at least one RKP.
2. **3-6 RKPs per lesson** (target 4). If a lesson has only 2 ACS elements, 3 RKPs is fine.
3. **One RKP can span multiple elements** if they are closely related.
4. **No phantom RKPs** — if the master module covers N distinct knowledge areas, the manifest must have N RKPs. Don't merge distinct topics into one RKP.

---

## 5. Bridge Key Rules (Critical)

Bridge keys connect DB1 (curriculum) to DB2 (FAA library) at search time.
Getting these wrong means the RAG verification step returns nothing.

1. **`far_references`** → maps to `reg_keys` in DB1 `structData`. Used by the Legal search lane.
2. **`bridge_keys`** → maps to `doc_keys` in DB1 `structData`. Used by Safety/Application search lanes.
3. **`bridge_keys` MUST be document-level tokens** matching DB2's `document_tags` vocabulary:
   - ✅ `FAA-H-8083-25C`, `AC 61-98D`, `AIM`, `14 CFR 91`
   - ❌ `FAA-H-8083-25C (PHAK Ch 6)`, `AIM 8-1-5`, `PHAK Ch 9`
4. **`bridge_keys` may NEVER be empty.** At least 1 document key is required per RKP.
5. **`far_references` may be empty** for non-regulatory topics (aerodynamics, physiology) — but **never write the literal "N/A"**; leave it as an empty array `[]`.

## 6. Execution Pipeline

When Daniel gives you a master module, execute these steps IN ORDER:

### Step 0: Read these references FIRST (before building any JSON)
- **`_docs/instruction_docs/rkp_creation_guide.md`** — the schema, field rules, and the reverse-contract
  (every fact a quiz will test must live in a `knowledge` field, not only the `lesson_overview`).
- **`_docs/instruction_docs/bridge_key_guide.md`** — the bridge-key contract (document-level tokens, DB2
  vocabulary, how to verify). `bridge_keys` may never be empty.
- **The source master module** in `curriculum_components/curriculum_modules/` (read it in full).

### Step 1: Analyze the Master Module
- Read the entire master module.
- List all ACS element codes found (PA.X.Y.Z).
- Cross-reference against the ACS Element to Lesson ID mapping.
- Confirm which lessons to create (and which already exist).

### Step 2: Present the Split to Daniel
- Show Daniel the proposed lesson split before building JSON.
- List: lesson_id → title → ACS elements → estimated RKP count.
- Wait for Daniel's approval.

### Step 3: Build the RKP JSON Files
- For each approved lesson, construct the full JSON.
- Extract `knowledge` from §1 (Oral Standard) of each element.
- Extract `far_references` from §4 Regs.
- Extract `bridge_keys` from §4 Docs — **normalized to document level**.
- Write the `why` field.
- Leave `knowledge_formatted` as `""`.
- Write the `lesson_overview` narrative.

### Step 4: Run `generate_knowledge_formatted.py`
```bash
cd curriculum_components/scripts
python generate_knowledge_formatted.py --all --write
```
This populates the `knowledge_formatted` fields using Gemini Pro.

### Step 5: Validate
- Confirm every ACS element has at least one RKP.
- Confirm `bridge_keys` are non-empty and document-level.
- Confirm JSON is valid and parseable.
- Run the bridge key verification skill if available.

### Step 6: Present to Daniel for Review
- Show the completed manifests.
- Highlight any decisions made (element groupings, bridge key selections).
- Wait for Daniel's final approval before committing.

## 9. Anti-Patterns (Do NOT Do These)

| ❌ Don't | ✅ Do Instead |
|---|---|
| Modify the `knowledge` field after Daniel approves | Treat it as immutable source of truth |
| Use chapter-level bridge keys (`PHAK Ch 6`) | Use document-level (`FAA-H-8083-25C`) |
| Leave `bridge_keys` empty | Always have ≥1 document key |
| Write `"N/A"` in any field | Use empty array `[]` or omit |
| Create RKPs without master module source | Wait for Daniel's master module |
| Skip the lesson split approval step | Always show Daniel the split first |
| Merge distinct knowledge areas into one RKP | Each distinct area gets its own RKP |
| Generate `knowledge_formatted` manually | Use the `generate_knowledge_formatted.py` script |
